## MySQL 集成验证

使用隔离的本地 MySQL Community Server 8.4.6，另外执行 `tests/Integration/ProcurementMysqlTest.php`，**6 项测试、72 个断言全部通过**。与默认测试集合计为 **47 项测试、321 个断言**。

这些测试先用项目原始 `install.sql` 初始化随机命名的临时数据库，再执行采购建表 SQL；供应商和任务队列仍使用模拟实现。测试确认：

- 原始安装 SQL 中全部旧表的结构和数据在新增采购表后保持一致；重复执行 SQL 和迁移不改变已有结构或数据，回滚迁移也保留旧表。
- 分别通过手写 SQL 和迁移创建的三张采购表，其 `SHOW CREATE TABLE` 结果完全一致（忽略测试写入产生的自增序号）。
- 两个进程并发确认同一笔付款时，只创建一笔采购，销量只增加一次。
- 两笔订单并发领取仅剩的一张本地卡时，只允许其中一笔交付该卡，另一笔进入采购。
- 两个采购进程争抢同一任务时，仅提交一次采购，并且只绑定一张已售卡密。
- 采购任务保存失败时，真实 MySQL 事务回滚付款、订单状态和销量；卡密关联失败后，由新的进程恢复本地入库，多次恢复也不会重复采购或插入卡密。

## 2026-10-29 代码审核与修复

审核范围为工作区全部未提交改动。主体实现与 ADR 一致：付款确认和采购记录同事务提交，下单前先持久化不可重发的状态，供应商响应先落库再入库卡密，重复通知和重复任务不会重复采购。本轮修复四处：

- `procurement:work` 遇到未捕获异常（如数据库短暂不可用）会直接退出。Supervisor 默认 `startretries=3`，进程启动后很快连续退出会进入 FATAL、不再拉起，已付款订单会一直停在「正在出卡」。现改为只记录异常类名和代码，10 秒后重试；收到 TERM、INT、QUIT 时先完成当前采购再退出，避免重启打断已提交的采购。`--once` 仍直接抛出异常。
- 供应商响应已保存、但订单已在后台被改为非「处理中」时，`deliver()` 原本直接返回，记录一直停在 `received`，恢复流程每轮重试且永不结束（积压超过 100 条还会挤占新记录）。现转为 `unknown`，原因 `order_not_processing`，保留响应供人工核对。
- 后台启用自动采购时，成本上限原本允许为 0，这样每笔缺货订单都会在付款后因询价超限失败。现要求大于 0。
- 库存定时任务的 `withoutOverlapping()` 默认锁 24 小时，任务被强制结束后库存快照会停更一天。改为 10 分钟过期。
